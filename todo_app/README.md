## Todo app

Application that displays a list of todos and a random image from `https://picsum.photos/1200`. Consists of a Next.js + React frontend, a Node.js + Hono backend and a PostgreSQL database which is used by the backend to store the todo data.

First run a Kubernetes cluster. In chapter 4  of the course we use [Google Kubernetes Engine](https://cloud.google.com/kubernetes-engine?hl=en) as a cloud service provider which offers free credits for practice use. After creating an account install [Google Cloud SDK](cloud.google.com/sdk/install) and [gke-gcloud-auth-plugin](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/cluster-access-for-kubectl#install_plugin). Kubernetes Engine API needs to be enabled, this can be done by running `gcloud services enable container.googleapis.com`. The propagation of the API activation may take a few minutes.

After the API is enabled you can create the cluster by running `gcloud container clusters create dwk-cluster --zone=europe-north1-b --cluster-version=1.36 --disk-size=32 --num-nodes=4 --machine-type=e2-small --gateway-api=standard`. The installation will take few minutes.

Check with `kubectl cluster-info` that your configuration is pointing to the remote cluster instead of a local one. If the configuration is still pointing at a local cluster we can correct this by running `gcloud container clusters get-credentials dwk-cluster --zone=europe-north1-b`.

The project uses a namespace called project. You can create the namespace by running `kubectl create namespace project`. You can set the namespace as the default namespace by running `kubectl config set-context --current --namespace=project` or if you have [kubens](https://github.com/ahmetb/kubectx) installed more conviniently with `kubens project`. You can check the current active namespace by checking current context namespace with `kubectl config view` or just by calling `kubens`.

Deploy with `kubectl apply -k .`. This creates the resources defined by the yamls listed in [`kustomization.yaml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/3.7/todo_app/kustomization.yaml) resources. The services define how the used application ports of the frontend and backend applications are connected to cluster internal network ports. The route resources define how the cluster internal services match to routing paths while the gateway resource defines a point of access to the cluster at which traffic is routed. The todo frontend application and the todo backend application have externally exposed routes while the postgres database is not exposed externally. The frontend requests  `/todo` path of the backend service. The todo list get is requested by the frontend directly using the kubernetes cluster internal routing and the post request for a new todo is done from the browser to the backend. [`The backend application route`](https://github.com/hinichijou/DevOpswithKubernetes/tree/3.7/todo_app/manifests/route_backend.yaml) defines a route rewriting rule where requests to the `/api` path are routed to the root path of the backend application.

The address assigned to the gateway will be the way to access the application. You can use `kubectl get gateway` to find out the address. `kubectl describe gateway *insert gateway name here*` can be used to get more detailed information about the gateway. The deployment might take several minutes and the reponses may be 404 and 502 before the application is available. [`healthcheckpolicies.yaml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/3.7/todo_app/manifests/healthcheckpolicies.yaml) defines `/health` as the health check path for the frontend and backend applications, a successful response is required for the gateway to start routing traffic to the service.

Google Kubernetes Engine will automatically provision a persistent disk for persistent volume claims if the storage class is not set in the persistent volume claim which is the strategy we will be using. [`manifests/persistentvolumeclaim_todoapp.yaml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/3.7/todo_app/manifests/persistentvolumeclaim_todoapp.yaml) requests a persistent volume resource to which the todo app uses to save the fetched image.

[`manifests/configmap_todoapp.yaml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/3.7/todo_app/manifests/configmap_todoapp.yaml) holds the environment variables for the todo application frontend and backend. See [backend readme](https://github.com/hinichijou/DevOpswithKubernetes/tree/3.7/todo_app/backend/README.md) and [frontend readme](https://github.com/hinichijou/DevOpswithKubernetes/tree/3.7/todo_app/todo_app_frontend/README.md) for more information on what the meaning of each of the environment variables is.

 The backend saves the todo data to a Postgres database with persistent storage which is run as a single replica StatefulSet defined in [`manifests/statefulset_postgres.yaml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/3.7/todo_app/manifests/statefulset_postgres.yaml). The env values required for the configuration of the database and the connection between backend and database can be found in [`manifests/configmap_postgres.yaml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/3.7/todo_app/manifests/configmap_postgres.yaml). The configMapGenerator in [`kustomization.yaml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/3.7/todo_app/kustomization.yaml) creates a file resource for the database initialization based on the contents of the [`manifests/init_todo_db.sql`](https://github.com/hinichijou/DevOpswithKubernetes/tree/3.7/todo_app/manifests/init_todo_db.sql) file. This file also defines the default todos displayed on the page. If deployed to a local cluster the setup should also contain a secret file  `secret_postgres.yaml` which is not in version control which has the name `secret-postgres-config` and defines the environment variable `POSTGRES_PASSWORD`. You can refer to the encrypted version of the file [`manifests/enc_secret_postgres.yaml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/3.7/todo_app/manifests/enc_secret_postgres.yaml) to see what kind of resource is expected. The encrypted version is decrypted and deployed in the [github deployment workflow](https://github.com/hinichijou/DevOpswithKubernetes/tree/3.7/.github/workflows/main.yaml).

[`manifests/wikipedia_todo_job.yml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/3.7/todo_app/manifests/wikipedia_todo_job.yml) defines a CronJob that sends a new todo post request to backend every hour with the content of "Read *random wikipedia link*". The random wikipedia link is obtained by sending a request to https://en.wikipedia.org/wiki/Special:Random. The job uses a Docker image that contains a single shell script, the contents of the image can be found from [`wikipedia_todo_job folder`](https://github.com/hinichijou/DevOpswithKubernetes/tree/3.7/todo_app/wikipedia_todo_job).

You can follow pod output logs with `kubectl logs -f *insert pod name here*`. You can use `kubectl get pods` to find out the pod name.

See the [monitoring folder](https://github.com/hinichijou/DevOpswithKubernetes/tree/3.7/monitoring) and the [monitoring readme](https://github.com/hinichijou/DevOpswithKubernetes/tree/3.7/monitoring/README.md) for instructions on how to run a monitoring setup for the deployment.

You can view the HTML page served from http://**enter gateway ip here**. The frontend fetches a new image from https://picsum.photos/1200 every 10 minutes. The frontend writes the image to persistent storage so it persists between application restarts. Frontend reads said image from the persistent storage and displays it. The backend has a get and post path for todos at `/todos` which is accessable at http://**enter gateway ip here**/api/todos. The frontend has the functionality for displaying the todos and adding a new todo. The Wikipedia todo CronJob is scheduled to post a new todo with a random Wikipedia link every hour.

You can remove the resources applied with the kustomization file with `kubectl delete -k .`. This doesn't delete the postgres persistent volumes which are not directly created in the manifests. You can delete them by finding the names with `kubectl get pvc` and calling delete directly for the persistent volume claims. You can also delete all resources of certain type, for example `kubectl delete --all deployments` would delete all deployment resources in the current namespace.

Delete the cluster with `gcloud container clusters delete dwk-cluster --zone=europe-north1-b` after use to avoid using credits while the cluster is not in use.

### Task 3.9 - DBaaS vs DIY: Pros and cons of the solutions in terms of meaningful differences
Task: We can either start using a Database as a Service (DBaaS) such as the Google Cloud SQL in our case or just use the PersistentVolumeClaims with our own Postgres images and let the Google Kubernetes Engine take care of storage via PersistentVolumes for us. Do a pros/cons comparison of the solutions in terms of meaningful differences. This includes at least the required work and costs to initialize, as well as the maintenance. Backup methods and their ease of usage should be considered as well.

In my answer I'm comparing Google Cloud database services and especially Google Cloud SQL to a diy solution because the course Chapter 4 heavily features Google Cloud and GKE and on the other hand the up- and downsides of the comparison are largely generalizable to other similar services as well.

The first meaningful difference that comes to mind is ability to run, test and configure the database locally. It is useful for the purpose of the course to be able to run and test your cluster locally and chapter 4 was said in the instructions to be the only one that strictly requires using a cloud deployment. If we are running our own Postgres deployment it is easy to run and test the pod locally which makes managing the configuration easier as we do not need to use different database configurations for local and remote use. This tips the scale automatically towards the diy solution for the purpose of this course.

The diy solution is likely to offer more flexibility. If we would like to move the cluster from the Google Cloud and use another provider the move is probably easier if we can deploy our own solution to cluster from another provider instead of having dependencies with multiple Google Cloud services. In general, having complete control over the database solution is a clear plus in favor of the diy solution. We can run any DBMS we have an docker image for with full freedom over its configuration. [Google Cloud SQL](https://cloud.google.com/sql?hl=en) for example supports only PostgreSQL, MySQL and SQL Server.

A diy solution naturally requires more work to set up and manage and if we think in terms of professional environments this means more manpower and personnel costs. Google Cloud SQL marketing material says that `We automate all your backups, replication, patches, encryption, and storage capacity increases`. This means that in exchange for the service costs we trivialize the effort required for managing scaling, robustness, backups, updates, security and storage. We are less likely to have service downtime or data loss when using a service that offers to automate all the previous for us. If our application scale grows we can update to a more expensive service tier instead of needing to spend time analyzing the cluster configuration and how much and what resources should we increase for suitable performance. For example Google [promises](https://cloud.google.com/sql?hl=en#pricing) 99.95% monthly uptime for CloudSQL Enterprise with < 60s of planned downtime and 99.99%  monthly uptime for CloudSQL Enterprise Plus with < 10s of planned downtime which are numbers that seem hard to reach when managing and monitoring our own solution. In terms of maintenance and application redeployments, having a service manage the storage instead of having our own volume claims is less error prone and [Cloud SQL also offers functionality to automatically increase storage size on demand](https://docs.cloud.google.com/sql/docs/mysql/storage-options-overview), in a diy solution we would have to modify our storage claims to take this into account.

Google also offers [AlloyDB](https://cloud.google.com/products/alloydb?hl=en#how-it-works) which they claim to be considerably more performant than a self hosted PostgreSQL server.

In terms of running costs Google Cloud SQL and AlloyDB have hourly rates for CPU hours, RAM usage, active and backup storage usage and a cost for network traffic per GB. You may have different rates for different machines and storage options and the pricing depends on region as well. Hosting a diy solution in a Google Cloud Kubernetes cluster also has charges for the same things but the billing is more understandable when we have the cluster being charged instead of adding a separate database service operation cost on top of it. You may also be billed for data traffic between two Google Cloud services depending on the region they are running in. Generally speaking the fact that the cloud service billing consists of several smaller running costs, some of which may or may not apply, makes the billing hard to understand and it should be monitored with care.

Regarding database initialization Google Cloud SQL offers [step-by-step instructions](https://docs.cloud.google.com/sql/docs/mysql/connect-kubernetes-engine) for connecting the database to a GKE cluster, since they are both Google Cloud services one can assume that they work together well. Google Cloud SQL also has a [console interface](https://docs.cloud.google.com/sql/docs/postgres/create-query-database) and the database view can be accessed through the same Google Cloud console interface as our GKE cluster and artifact repository. One could say that it is not hard to initialize a basic postgres service to run in our own cluster replicating the instance with a StatefulSet and reserving persistent storage with a claim template either but on this course the database itself has been running on a pretty much default configuration, there is considerable work in understanding the configuration options and considering what kind of configuration is the best fit for our application. I would say the DBaaS solution offers a lower learning curve for initialization with the database state being presented in an easily understandable format in the console. Database initializations are less error prone and instead of having to encrypt, configure and share our own secrets in the pipeline this is handled securely between the Google Cloud services using the Cloud SQL Auth Proxy.

Google Cloud SQL offers [clear instructions](https://docs.cloud.google.com/sql/docs/postgres/backup-recovery/manage-standard-backups) for taking backups on demand or scheduling automated backups. For our diy solution we can for example configure a CronJob that takes database backups on a schedule. The gcloud API for managing the backups seems quite clear and concise and while running our own job is not difficult it is likely that the required effort to configure a backup scheme is considerably more with our own solution requiring more testing, having more points of failure and requiring more manual management and monitoring.

It is obvious that Google Cloud SQL isn't the most feasible solution for a single developer small project like the one we have been working on this course but at the same time the strengths of Kubernetes in the first place aren't in running small scale single developer projects but in the scalability and availability of larger projects with considerable traffic. For larger projects Google Cloud SQL offers a lot of useful functionality and frees developers to work on something else than the cluster database configuration, management and monitoring while making the database more accessable and hence requiring less expertise in its operation, all of this resulting in saved operating costs. On the other end of the scale on massive projects where you have dedicated personnel and expertise you might start to get cost benefits from running and configuring your own solutions instead of paying the running operation costs for cloud services.
