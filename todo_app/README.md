## Todo app

Application that displays a list of todos and a random image from `https://picsum.photos/1200`. Consists of a Next.js + React frontend, a Node.js + Hono backend and a PostgreSQL database which is used by the backend to store the todo data.

First run a Kubernetes cluster. In chapter 5 of the course we move back to using a local cluster. For example with [k3d](https://github.com/k3d-io/k3d) you can create a cluster with `k3d cluster create -p 8081:80@loadbalancer --agents 2 --k3s-arg '--disable=traefik@server:0'`. Local port 8081 is opened to port 80 in load balancer. `--disable=traefik@server:0` is required for the gateway api installation. If the cluster already exists it can be started with `k3d cluster start`.

Check with `kubectl cluster-info` that your configuration is pointing to the local cluster. If it is not we can correct this by running `kubectl config get-contexts` to get the name of the context and set it with `kubectl config use-context *context-name*`.

The cluster uses a gateway resource which doesn't exist in a k3d cluster out of the box. Install the Envoy gateway using the instructions from the [envoy_gateway folder](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/services/envoy_gateway).

The cluster uses a gateway resource to handle inter-namespace routing from a single externally exposed port to different services. Apply the infra resources using the instructions from [infrastructure_manifests folder](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/infrastructure_manifests). This also creates the necessary namespaces.

For the PersistentVolumes to work you first need to create the local path in the node we are binding it to. We can create the folders `/tmp/kube/todoapp-staging` `/tmp/kube/todoapp-production` in container `k3d-k3s-default-agent-0` with `docker exec k3d-k3s-default-agent-0 mkdir -p /tmp/kube/todoapp-staging` and `docker exec k3d-k3s-default-agent-0 mkdir -p /tmp/kube/todoapp-production`.

Create persistent volumes with `kubectl apply -f persistent_volume_manifests`. As PersistentVolumes are often maintained by cluster administrators rather than developers and those are not application specific the definitions are separated from the application manifests. Applying creates a local persistent volumes for staging and production to path `/tmp/kube`.

The application uses [NATS](https://docs.nats.io/) for messaging. Install NATS with the instructions [in the nats service folder](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/services/nats).

To automate the deployment Argo CD can be added to the cluster using the instructions from [argocd service folder](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/services/argocd).`manifests/secret_discord_webhook.yaml` needs to be created and deployed to the namespace beforehand with `kubectl apply -f manifests/secret_discord_webhook.yaml` since it is not pushed to GitHub and is not part of the automated deployment. More details about the file can be found further in the instructions. Argo CD watches for manifest changes in the defined git repo folder and redeploys the application if necessary.

[build-deploy-on-push.yaml](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/.github/workflows/build-deploy-on-push.yaml) defines GitHub workflow for building the application images and updating the correct images to kustomization files. The same workflow handles the deployment for both the todo app and log output pingpong application: the images are only built if there are changes to the related folders and the Argo CD is configured to watch for manifest changes at the root folder of each application. The applications cannot be deployed at the same time currently because the routes overlap but I didn't change the routes in case the tasks require the applications to be served specifically at the current routes. [See readme](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/.github/workflows/README.md) for more detailed description.

To deploy manually use `kubectl apply -k .` in the [staging](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/overlays/staging) or [production](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/overlays/prod) folder, which creates the resources listed in the `kustomization.yaml` located in the folder. The services define how the used application ports of the frontend and backend applications are connected to cluster internal network ports. The route resources define how the cluster internal services match to routing paths while the gateway resource defines a point of access to the cluster at which traffic is routed. The todo frontend application and the todo backend application have externally exposed routes while the postgres database is not exposed externally. The frontend requests  `/todo` path of the backend service. The todo list get is requested by the frontend directly using the kubernetes cluster internal routing and the post request for a new todo and the put request for marking a todo done is done from the browser to the backend. [The backend application route](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/base/manifests/route_backend.yaml) defines a route rewriting rule where requests to the `/api` path are routed to the root path of the backend application.

[`persistentvolumeclaim_todoapp_prod.yaml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/overlays/prod/patches/persistentvolumeclaim_todoapp_prod.yaml) and [`persistentvolumeclaim_todoapp_staging.yaml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/overlays/staging/patches/persistentvolumeclaim_todoapp_staging.yaml) request persistent volume resources to be used by the todoapp frontend to save the displayed image, the data written persists between application runs. Because the PersistentVolume gets claimed by a specific PersistentVolumeClaim deployment, if you remove the resources but want to use the same persistent volume to keep the data stored for a new deployment you should delete the `claimRef` entry from PV specs, so as new PVC can bind to it. This should make the PV Available. This can be done with bash command `kubectl patch pv todoapp-*environment here*-pv -p '{"spec":{"claimRef": null}}'`.

[`configmap_todoapp.yaml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/base/manifests/configmap_todoapp.yaml) holds the environment variables for the todo application frontend and backend. See [backend readme](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/backend/README.md) and [frontend readme](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/todo_app_frontend/README.md) for more information on what the meaning of each of the environment variables is.

 The backend saves the todo data to a Postgres database with persistent storage which is run as a single replica StatefulSet defined in [`statefulset_postgres.yaml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/base/manifests/statefulset_postgres.yaml). The env values required for the configuration of the database and the connection between backend and database can be found in [`configmap_postgres.yaml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/base/manifests/configmap_postgres.yaml). The configMapGenerator in [`kustomization.yaml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/base/kustomization.yaml) creates a file resource for the database initialization based on the contents of the [`init_todo_db.sql`](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/base/manifests/init_todo_db.sql) file. This file also defines the default todos displayed on the page. If deployed to a local cluster the setup should also contain a secret file  `secret_postgres.yaml` which is not in version control which has the name `secret-postgres-config` and defines the environment variable `POSTGRES_PASSWORD`. You can refer to the encrypted version of the file [`sealed_secret_postgres.yaml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/base/manifests/sealed_secret_postgres.yaml) to see what kind of resource is expected.

 The [backend](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/backend) publishes a NATS message on `/todos` POST and PUT with the subject defined in [configmap_nats.yaml](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/base/manifests/configmap_nats.yaml). The broadcaster in turn subscribes to this subject. See the [broadcaster folder](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/broadcaster) and the [broadcaster readme](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/broadcaster/README.md) for the broadcaster implementation and an explanation of the environment variables. The broadcaster expects a file `secret_discord_webhook.yaml` to which the [broadcaster deployment](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/base/manifests/deployment_broadcaster.yaml) refers with the name `secret-discord-webhook-config` which contains the value for the environment variable `EXTERNAL_SERVICE_URL`. Since the course practice webhook has a instruction written in capitals to not commit the hook to GitHub I decided to err on the side of caution and did not to do so even with an encrypted version.

[`wikipedia_todo_job.yaml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/base/manifests/wikipedia_todo_job.yaml) defines a CronJob that sends a new todo post request to backend every hour with the content of "Read *random wikipedia link*". The random wikipedia link is obtained by sending a request to https://en.wikipedia.org/wiki/Special:Random. The job uses a Docker image that contains a single shell script, the contents of the image can be found from [`wikipedia_todo_job folder`](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/wikipedia_todo_job).

[`db_backup_job.yaml`](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/base/manifests/db_backup_job.yaml) defines a CronJob that takes a backup of the postgres database every 24 hours and saves the result to Google Cloud Storage bucket. The job uses a Docker image that contains a single shell script, the contents of the image can be found from [`db_backup_job folder`](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/db_backup_job). See [`db_backup_job readme`](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/db_backup_job/README.md) for more detailed explanation. The job is written to authenticate as a Google Cloud cluster internal job using Workload Identity Federation so the job doesn't work when running in a local cluster.

You can follow pod output logs with `kubectl logs -f *insert pod name here*`. You can use `kubectl get pods` to find out the pod name.

See the [monitoring folder](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/monitoring) and the [monitoring readme](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/monitoring/README.md) for instructions on how to run a monitoring setup for the deployment.

You can view the HTML page served from http://localhost:8081/todoapp-staging or http://localhost:8081/todoapp-prod. The frontend fetches a new image from https://picsum.photos/1200 every 10 minutes. The frontend writes the image to persistent storage so it persists between application restarts. Frontend reads said image from the persistent storage and displays it. The backend has get, post and put paths for todos at `/todos` which is accessable at http://localhost:8081/todoapp-staging/api/todos or http://localhost:8081/todoapp-prod/api/todos. The frontend has the functionality for displaying the todos, adding a new todo and marking a todo as done. The Wikipedia todo CronJob is scheduled to post a new todo with a random Wikipedia link every hour.

You can remove the resources applied with the kustomization file with `kubectl delete -k .`. This doesn't delete the postgres persistent volumes which are not directly created in the manifests. You can delete them by finding the names with `kubectl get pvc` and calling delete directly for the persistent volume claims. You can also delete all resources of certain type, for example `kubectl delete --all deployments` would delete all deployment resources in the current namespace. Deleting the whole namespace with `kubectl delete namespace project` will also delete all the resources in the namespace.

The cluster can be stopped with `k3d cluster stop` and started with `k3d cluster start`. The cluster can be deleted with `k3d cluster delete`.

### Task 4.9
#### Instructions

Enhance the Project setup as follows:

* Create two separate environments, production and staging that are in their own namespaces
* Each commit to the main branch should result in deployment to the staging environment
* Each tagged commit results in deployment to the production environment
* In staging the broadcaster just logs all the messages, it does not forward those to any external service
* In staging database is not backed up
* You may assume that secrets are readily applied outside of the ArgoCD

#### Solution

First follow the readme setup instructions until the step where Argo CD is set up.

Since I separated creation of the namespaces to a separate infrastructure creation step I added two new namespaces to [the namespace infrastructure manifest](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/infrastructure_manifests/manifests/namespaces.yaml): `project-staging` and `project-production` (naming is to separate from possible exercise app staging/production setup).

Based on the material we would like to create two Argo CD application resources, one targeting the overlays/prod folder and the other overlays/staging. Argo CD seems to offer [ApplicationSets](https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/) that provide `The ability to use a single Kubernetes manifest to deploy multiple applications from one or multiple Git repositories with Argo CD` which seems to be just about what we would need. Since Applications are part of the Argo CD configuration I placed the manifest to [services/argocd/applications folder](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/services/argocd/applications/applicationset_todo_app.yaml). Change working directory to that directory and apply with `kubectl apply -f applicationset_todo_app.yaml`.

Based on the previous material I took `Each commit to the main branch should result in deployment to the staging environment` to mean that the staging workflow works the same as in task 4.8 and `Each tagged commit results in deployment to the production environment` means that the tagging triggers a workflow run that causes image updates to the production kustomization file which Argo CD following the prod overlay folder then picks up although Argo CD could also be [configured to follow tags](https://argo-cd.readthedocs.io/en/stable/user-guide/tracking_strategies/#tag-tracking) which would make the deployments strictly happen only on tag updates while my interpretation also causes Argo CD to pick up changes to related manifests on regular commits. However Argo CD supports only semantic versioning which means that supporting redeployment on any pushed tag is impossible because the commited tags would have to adhere to the standard unless making a workflow that would re-tag the commit in the correct format.

I decided to keep the workflow basically the same, the staging builds are built every time there are changes to the relevant folders. For production builds I decided to build all of the images for every tag to keep the logic simple. I build these to different dockerhub repositories called *image-name*-staging and *image-name*-production, with the staging image getting the tag of the git commit causing the build and production build getting the tag triggering the build as the image tag. While this does create production images with overlapping content the logic of the repository should be easy to follow with images for each task. See [build-deploy-on-push.yaml](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/.github/workflows/build-deploy-on-push.yaml) for the workflow definition.

For the broadcaster requirement I divided `secret_discord_webhook.yaml` to `secret_discord_webhook_staging.yaml` and `secret_discord_webhook_prod.yaml` but since it was ok to assume that secrets are readily applied outside of the ArgoCD the change isn't reflected in the repository or manifests in any way. `secret_discord_webhook_staging.yaml` has `EXTERNAL_SERVICE_URL` set to `""` which effectively results in the messages just being logged. `secret_discord_webhook_prod.yaml` has `EXTERNAL_SERVICE_URL` set to the actual course discord webhook. These need to be applied to the correct namespaces before deployment with `kubectl apply -f secret_discord_webhook_staging.yaml -n project-staging` and `kubectl apply -f secret_discord_webhook_prod.yaml -n project-production`. It would be possible to use Sealed Secrets but since it was forbidden to post the hook to GitHub I decided to not to do so even with an encrypted version. As explained in [task 4.7.](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.7/log_output_ping-pong_application#task-47) I decided not to use repository secrets since Argo CD documentation seems to consider it a bad practice.

Based on the material it seemed that the requirement of the database not being backed up in staging is best done so that the db backup job has a [staging overlay](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/overlays/staging/patches/db_backup_job_staging.yaml) with `suspend: true`. This means that the database backup job could be scheduled in staging for example for testing by setting the field to false. The database backup job itself is still in the same state as the task where it was featured which means that it is written to work inside a GKE cluster instead of a local cluster but I did not spend time on converting it to a local cluster version since I didn't think it was the point in this task.

I added separate [persistent volumes](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/persistent_volume_manifests/persistentvolume.yaml) for both of the environments and added patches for the [base persistent volume claim](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/base/manifests/persistentvolumeclaim_todoapp.yaml) for [staging](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/overlays/staging/patches/persistentvolumeclaim_todoapp_staging.yaml) and [production](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/overlays/prod/patches/persistentvolumeclaim_todoapp_prod.yaml).

To be able to access both the staging and production applications while they are deployed at the same time I decided to change the routes so that there is no overlap. It seems that the route resources don't support strategic merge so I removed the base route resources and added separate route resource files for [staging](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/overlays/staging/resources) and [production](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/overlays/production/resources). Staging is available at http://localhost:8081/todoapp-staging/ and production at http://localhost:8081/todoapp-prod/. For the Next.js frontend to work this required defining the [root path](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.9/todo_app/todo_app_frontend/next.config.ts) of the application on build time.
